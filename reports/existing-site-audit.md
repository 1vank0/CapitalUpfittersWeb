## 3. Lead / Quote Journey (traced by reading code only — no submissions made)

**Architecture:** `attribution.js` (persistent first-touch capture) → `lead-form.js` (single shared submit controller, attaches to every `form[data-cms-form]`) → `POST /api/lead` (Vercel function) → durable persistence (`capital-upfitters-next.vercel.app/api/leads/`, server-to-server) + Resend transactional email. `quote-form.js` is UI-only (audience tabs + service picker) and deliberately does not submit, to avoid the double-submission bug the QA doc alludes to.

**Forms and their mapping** (`api/lead.js` `SUPPORTED_FORMS`, lines 52–58):
| Form id | `data-cms-form` | Maps to | Page |
|---|---|---|---|
| `quote-retail` | `retail` | `retail` | `quote.html` |
| `quote-fleet` | `fleet` | `fleet` | `quote.html` |
| `quote-dealer` | `dealer` | `dealer` | `quote.html` |
| `callback-form` | `retail` | `retail` | `contact.html` |
| `apply-form` | `dealer` | `dealer` | `dealer-government.html` |

**Retail lead flow:** visitor fills `quote-retail` panel (or `callback-form` on `contact.html`) → `lead-form.js` injects 19 hidden attribution fields + a honeypot field → on submit, builds a payload with an idempotency key (`crypto.randomUUID()`) and a content fingerprint (FNV-1a-style hash) so a resubmit with identical content reuses the same idempotency key, but any change rotates it → `POST /api/lead` → server validates origin (allowlist + same-host preview support), rate-limits (8/15min/IP via `localRateBuckets`), validates JSON schema (size caps, email/phone regex, service slug regex `/^[a-z0-9][a-z0-9_-]*$/i`, max 12 services) → persists to the durable store over an HMAC-signed bridge header (`X-Capital-Bridge-Signature`, real client IP forwarded) → sends a branded HTML email via Resend → returns `{ok, persisted, delivered, delivery_mode, reference}`.

**Fleet and dealer/government leads** follow the identical code path with a different `form_type`/`audience` discriminator; there is no separate contract — same `/api/lead`, same validation, same response shape. This is a well-designed single-endpoint pattern.

**Failure semantics** (confirmed by reading `api/lead.js` lines 989–1121, matches `docs/lead-flow-qa.md` §8's failure-state test list): persistence-only failure → HTTP 200, `persisted:false`, `delivered:true`, `delivery_mode:"email_fallback"` (customer not blocked); delivery failure after successful persistence → HTTP 502, `delivered:false`; malformed/oversized/invalid-origin requests → 4xx and no side effects.

**Service picker sync:** `quote-form.js` maintains a canonical `SERVICES` array (16 entries) mapping legacy checkbox label strings to backend-safe slugs, syncs bidirectionally between chip grid and the retail/fleet/dealer checkbox panels, persists selection to `localStorage['cu:quote-cart:selected']`, and supports `?service=X,Y` / `?audience=fleet|dealer` deep links.

**Automated contract test — inconclusive in this sandbox:**
- Evidence: ran `node --test tests/lead-flow-contract.test.js` locally. The suite fully mocks `global.fetch` (verified in the test file, lines ~120–140: sets fake `LEAD_PERSISTENCE_URL='https://persistence.test/...'`, fake `RESEND_API_KEY`, and reassigns `global.fetch` per test) — **no real network calls were made to any live endpoint**, consistent with the "no live-API" constraint on this audit.
- Result: 15 of 28 tests passed; 13 were cancelled by the Node test runner with `error: 'Promise resolution is still pending but the event loop has already resolved'`, starting around test #16.
- Severity: Medium. This may be a sandbox/environment artifact (e.g., timer/AbortController behavior differs here) rather than a real regression, but it means **this audit cannot confirm the "22/28" (or current "28 total") pass count the QA doc expects** in this environment.
- Proposed correction: re-run `node --test tests/lead-flow-contract.test.js` in Ivan's normal local/dev environment before any redesign work touches `quote.html`, `lead-form.js`, `attribution.js`, or `api/lead.js`, per the QA doc's own cadence rule.
- Priority: High (gate before touching lead-flow files), but not a redesign blocker by itself.

## 4. Content Duplication / Obsolete Content

### 4.1 Dead legacy CMS still actively called by 16 live pages — **High severity**
- Evidence: `var CMS_BASE = 'https://capital-upfitters-6iq57bc73-ivan-s-projects-fc67197c.vercel.app';` followed by an unconditional `fetch(...)` appears, unguarded, in: `gallery.html`, 11 service pages (`bedliner.html`, `ceramic-coating.html`, `commercial-wraps.html`, `exterior.html`, `hitches.html`, `industrial-coatings.html`, `mobile-detailing.html`, `running-boards.html`, `tonneau.html`, `undercoating.html`, `window-tinting.html`), and 4 location pages (`rockville-md.html`, `bethesda-md.html`, `silver-spring-md.html`, `gaithersburg-md.html`). Total: 16 pages fire a live client-side fetch to this domain on every page load.
- By contrast, `index.html`, `contact.html`, `dealer-government.html`, `fleet.html`, and `start-here.html` reference the same `CMS_BASE` but have an explicit early `return;` with the comment `// PHASE-1 DISABLED: stale CMS preview URL threw CORS errors. Re-enable by removing this line + updating URL.` — so those 5 pages are correctly no-ops.
- This is the *exact* domain `docs/lead-flow-qa.md` §8 calls a "dead API" and says was disabled in Phase 1 ("No requests to the old dead API... Phase 1 disabled these") — but that disabling was only applied to 5 of 21 pages that reference it, not all of them.
- User impact: silent-fail (wrapped in `.catch()`), so no visible breakage — but every visit to 16 pages fires an extra cross-origin network request to a Vercel deployment nobody actively maintains.
- Business impact: minor performance/privacy cost today; real risk if that Vercel project slug is ever deleted and reused by an unrelated third party (dangling-subdomain-style exposure), plus console/network noise that will confuse anyone debugging the site.
- Proposed correction: remove the dead `CMS_BASE` fetch blocks entirely from all 16 affected pages (don't just add the same disabling guard — delete the dead code) as part of the redesign rewrite, rather than carry it forward.
- Expected benefit: fewer requests per page load, no dangling third-party dependency, cleaner codebase for the next agent/dev.
- Priority: High (easy to fix once each page is being rewritten anyway; not a hotfix-now item since it fails silently).

### 4.2 `cms-data.json` + Tina CMS scaffolding — orphaned, not wired to rendering — **Medium-High severity**
- Evidence: `grep -rl "cms-data.json" *.js *.html services/*.html` → zero matches. The file exists (190KB) with fully-populated `services`, `geoPages`, `testimonials`, `faqs`, `settings`, etc., but nothing loads it at request or build time in this static repo.
- Business impact: this represents completed CMS-migration content work (per `PROJECT-CONTEXT.md`, PR #2) that isn't actually powering the live pages — the live pages are still 100% hand-hardcoded HTML. Anyone editing content today has to edit HTML directly; Tina's promise (edit-content-without-touching-HTML) isn't realized yet.
- Proposed correction: this is a scope decision for Ivan, not something to silently "fix" — either (a) genuinely wire pages to consume `cms-data.json` at build time as part of the redesign, or (b) treat it as reference content to hand-port into the new static pages and leave the Tina wiring for a later phase. Flag as an open question in `project-memory/OPEN-QUESTIONS.md`-style decision, not assumed.
- Priority: Decision needed before/at start of implementation phase, not audit-blocking.

### 4.3 Orphaned files
- `preview.html`, `products-section.html` (root) — not linked from any page, not in `sitemap.xml`. `products-section.html`'s header comment claims it's "Generated from products.json — 58 products + 4 bundles," but `products.json` does not exist anywhere in the repo. `preview.html` still imports the pre-redesign Barlow Condensed font stack, confirming it predates the Apple-palette merge.

### 4.4 Location pages — expected duplication, not a bug
- Evidence: diffing `locations/rockville-md.html` against `locations/bethesda-md.html` (with city names/zips normalized) shows the two files are almost line-for-line identical in CSS and structure, differing mainly in copy strings, schema `addressLocality`/`postalCode`, and hero image alt text. ## 5. SEO / Schema — Present vs. Missing

**Present, sitewide:**
- Canonical `<link rel="canonical">` on every page checked.
- Open Graph + Twitter card meta tags on every page.
- `robots` meta (`index, follow`).
- JSON-LD types found in use (counts from a sitewide grep of `"@type"`): `City` (103), `Question`/`Answer` (85 each, FAQPage content), `ListItem`/`BreadcrumbList` (76/28), `PostalAddress` (25), `Organization` (24), `AggregateRating` (19), `FAQPage` (18), `Service` (17), `LocalBusiness` (17), `AggregateOffer` (13), `State` (9), `AutoRepair` (8), `OpeningHoursSpecification`/`GeoCoordinates` (7 each), `County` (2), `GeoCircle`/`AdministrativeArea` (1 each).
- `sitemap.xml` (35 URLs) + `robots.txt` pointing to it.

**Issues found:**

1. **Broken `og:image` on every page — High severity.**
   - Evidence: every page's `<meta property="og:image" content="https://www.capitalupfitters.com/assets/og-default.png">` (37 occurrences across the codebase, confirmed via `grep -h "og:image"`), but `assets/og-default.png` does not exist — `assets/` contains only `amp-powerstep.mp4`. The actual OG-style images that do exist are `/og.png` and `/og.svg` at repo root.
   - User impact: every social share (Facebook, LinkedIn, iMessage, Slack unfurls, etc.) of any page on this site shows a broken image or no preview image.
   - Business impact: materially hurts click-through on any shared link — for a lead-gen local business, social/referral shares are a real channel.
   - Proposed correction: point `og:image` at the real `/og.png` (with absolute URL) sitewide, or generate and ship the missing `assets/og-default.png`.
   - Expected benefit: working link previews everywhere.
   - Priority: High — trivial fix, large and easily-verified payoff.

2. **Malformed `<meta name="description">` on 2 pages — High severity.**
   - Evidence, `locations/rockville-md.html` line 14: `content="Capital Upfitters is Rockville's neighborhood upfitter at 12019 Nebel Street. Bedliners from $575, hitches, ceramic coating & more. Walk-ins welcome Mon–Fri."s local upfitting shop at 12019 Nebel Street. Bedliners, hitches, ceramic, undercoating — walk-ins welcome Mon–Fri."s neighborhood vehicle upfitter — right here at 12019 Nebel Street. Bedliners, hitches, ceramic coatings & fleet services. Walk-ins welcome Mon–Fri 9:30am–4:30pm.">` — three separate draft copies of the description appear to have been concatenated with two stray `"s` sequences that close the attribute early and leave invalid trailing text before the tag's `>`.
   - Evidence, `start-here.html` line 14: same pattern — `content="Tell us what brings you in — personal vehicle, fleet, or dealer account. Capital Upfitters in Rockville, MD gets you to the right service fast."ll point you to the right services, pricing, and contact path. Personal vehicle, fleet, or dealer — we have a solution.">`
   - Checked all 4 location pages individually — only `rockville-md.html` has this defect; `bethesda-md.html`, `silver-spring-md.html`, `gaithersburg-md.html` are clean.
   - User impact: browsers will parse only the text up to the first stray `"`, so the actual rendered/indexed description is truncated mid-sentence at `...Walk-ins welcome Mon–Fri."` (Rockville) and `...gets you to the right service fast."` (start-here) — search engines will either use this truncated version or discard it and auto-generate a snippet from body text.
   - Business impact: degraded SERP click-through for two important pages (the primary geo page and the top-of-funnel router page).
   - Proposed correction: replace with a single clean description string on each page.
   - Expected benefit: correct, full meta description restored on both pages.
   - Priority: High — quick, isolated, high-confidence fix.

3. **`AutoRepair` used as the JSON-LD business type — Medium severity.**
   - Evidence: `"@type": "AutoRepair"` appears 8 times site-wide, including the homepage's primary `LocalBusiness` block.
   - Issue: Capital Upfitters is a vehicle-upfitting/accessories/protective-coatings shop, not a mechanical repair shop. `AutoRepair` (a Schema.org `LocalBusiness` subtype specifically for repair services) is a content/type mismatch that could affect which rich results Google considers eligible and how the entity gets categorized.
   - Proposed correction: evaluate `AutomotiveBusiness` (the more general parent type) or another closer-fitting subtype during the schema-plan phase.
   - Priority: Medium — feeds directly into the upcoming `reports/schema-plan.md` deliverable.

4. **Hardcoded, unverified `aggregateRating` baked into JSON-LD — Medium-High severity (compliance risk).**
   - Evidence: `index.html`'s `LocalBusiness` JSON-LD includes `"aggregateRating": {"ratingValue": "5.0", "reviewCount": "96"}` (19 `AggregateRating` occurrences site-wide in total).
   - Cross-reference: `project-memory/REQUIREMENTS.md` explicitly lists "review ratings/counts" among the "Trust claims requiring verification before publishing."
   - Business impact: publishing a specific, precise review count/rating in structured data that can't currently be substantiated is a real risk — Google's structured-data guidelines require review/rating markup to reflect genuine, verifiable reviews, and mismatches between claimed and demonstrable ratings can trigger a manual action against rich-result eligibility.
   - Proposed correction: do not carry this number forward into the redesign until it's verified against an actual review source (Google Business Profile, etc.); this is already tracked as a trust claim to verify — flagging here so schema work doesn't accidentally re-embed an unverified number.
   - Priority: High — verify-before-publish, per existing `REQUIREMENTS.md` policy.

5. **URL/entity inconsistency: `www` vs. non-`www`.**
   - Evidence: canonical tags sitewide use `https://www.capitalupfitters.com/...`, but `index.html`'s JSON-LD `"url"` field is `"https://capitalupfitters.com"` (no `www`). The sitemap has the same split (§1, `stealth-hitches.html` entry).
   - Priority: Low-Medium — worth normalizing on one canonical host during the redesign.

6. **No `Article`/`BlogPosting` schema on any blog post.**
   - Evidence: `grep -o '"@type": "[A-Za-z]*"' blog/*.html` returns nothing for any of the 5 posts or `blog/index.html` — no JSON-LD of any kind was found on blog pages.
   - Business impact: missed opportunity for blog rich results (author, datePublished, etc.) and weaker topical signal for AEO/GEO surfaces.
   - Priority: Medium — feeds the upcoming `schema-plan.md`.

## 7. Hardcoded values that should be data-driven

- **Phone number** `(301) 304-1419` is hardcoded as literal text/attribute in at least 38 files (`grep -rl "(301) 304-1419"`), plus 25 more occurrences of the `tel:13013041419` link format, plus JS fallback strings inside `lead-form.js` (`callLink.href = 'tel:3013041419'`, line 119) and `api/lead.js`. No single source of truth — a phone-number change today means editing 38+ files by hand.
- **Address** `12019 Nebel Street` / `12019 Nebel St` appears hardcoded in at least 36 files.
- **Pricing** (`$575` starting bedliner price, etc.) is hardcoded per service page and also duplicated inside the orphaned `cms-data.json` (§4.2) — two sources of truth that already disagree with nothing keeping them in sync, since one is unused.
- **Script path inconsistency**: `attribution.js`/`lead-form.js` are loaded as root-absolute (`src="/attribution.js"`, 39 occurrences each), while `animations.js` is loaded inconsistently — root-relative in some places, `./animations.js` or `animations.js` (bare relative) in others (26 + 7 + 3 occurrences respectively) depending on page depth. Works today because paths happen to resolve correctly per directory depth, but it's a fragile, easy-to-break pattern the redesign should standardize (pick one convention, e.g. root-absolute everywhere).
- **`CMS_BASE`** dead-domain string is itself hardcoded independently into 16+ files rather than being a single config value (moot once §4.1 is fixed, but illustrates the pattern).

Proposed correction for all of the above: centralize business-identity constants (phone, address, hours, email) into one data source consumed by all pages at build time — this is exactly what `cms-data.json`'s `settings` block already contains (business_name, phone, email, address, hours, social URLs) but isn't wired up (§4.2). Whatever the redesign's content pipeline ends up being, this is the natural place to fix it once.
